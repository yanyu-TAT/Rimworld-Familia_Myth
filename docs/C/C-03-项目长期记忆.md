- 游戏程序集引用 Steam 本地路径，构建/测试仅本机可完成，CI 不可编译。
- 远程仓库 GitHub `yanyu-TAT/Rimworld-Familia_Myth`，分支 main。

- **隐式 using 已开启**：`Familia_Myth.csproj` 设了 `<ImplicitUsings>enable</ImplicitUsings>`（SDK 风格工程 + net472），编译期自动生成 GlobalUsings。**实际列表只有 6 项**（取证：`Familia_Myth/obj/Debug/Familia_Myth.GlobalUsings.g.cs`）：`System` / `System.Collections.Generic` / `System.IO` / `System.Linq` / `System.Threading` / `System.Threading.Tasks`。**除这 6 项外的命名空间都需自行 using**——`System.Reflection`（Harmony `TargetMethod()` 的 `MethodBase`、`AccessTools`）、`System.Text`（`StringBuilder`）等；特别注意 **`System.Net.Http` 不在其中**（它属 `Microsoft.NET.Sdk.Web` 的默认项，本项目是 `Microsoft.NET.Sdk`）。取证：`Patch_ManaGain.cs`、`Hediff_Pharna.cs` 等直接使用 `Exception`、`FirstOrDefault` 而文件头无对应 using。
- **Harmony 补丁在模组构造函数里一次性注册**：`FamiliaMythMod` 构造函数末尾调用 `ApplyHarmonyPatches()` → `new Harmony(Content.PackageIdPlayerFacing).PatchAll(typeof(FamiliaMythMod).Assembly)`，整体包 try-catch + `Log.Error("[FamiliaMyth] Failed to apply Harmony patches: ...")`。因此**新增补丁类零配置生效**，只需是（顶层或嵌套的）静态类且带 `[HarmonyPatch]`；`PatchAll` / `new Harmony` 只允许出现在该构造函数路径上，别处再写会产生重复补丁。
  - Harmony id 沿用 `Content.PackageIdPlayerFacing`（即 `yanyu.familiamyth`），与旧运行日志里的补丁归属标记一致。
  - 注册失败（如 `TargetMethod()` 返回 null）打的是本模组自己的 `[FamiliaMyth] Failed to apply Harmony patches` 红字——排查补丁失效先搜这一句。

## 运行时与构建运维约定

- **`Player.log`** **时效性**：日志文件由用户在本地运行时产生，**需要用户手动刷新才会更新**；未刷新时为旧版本运行日志，Agent 分析时须先向用户确认其时效，不能当作当前代码状态的证据。
- **`.shader`** **打包**：`Materials/` 下的 `.shader` 无法直接在游戏内生效，**需用户在 Unity 中手动打包为 AssetBundle**（`AssetBundles/`）才能生效。**修改** **`.shader`** **后必须提醒用户重新打包**，否则改动不会进入游戏。导出脚本存于 `D:\CODE\Shaders\My project\Assets\Editor\BuildAssetBundle.cs`（菜单 `Tools/Build Mod AB`）。
  - **1.7 必须包含 Vulkan 变体**：Waylith 引擎跑在 Vulkan 上，`AssetBundleReader.BuildShader` 取不到 Vulkan 变体时只打一句警告、退回引擎默认 shader（现象：自定义效果整体丢失，`Player.log` 出现 `no Vulkan variant in this bundle ... it draws with the engine default`）。导出脚本须确保目标平台的 Graphics APIs 含 Vulkan（Windows 目标勾选 Vulkan；或另导 `..._linux` 兄弟包 —— Waylith 会按 `_win` / `_mac` → `_linux` 的命名规则回退取用），并带 `ForceRebuildAssetBundle`，否则会复用旧的变体缓存。
  - **1.7 的文本后端不提供中文字形**：`ImGuiTextMeshProBackend` 只烘焙 ASCII 32-126 与 Latin-1 160-255，且 `TryGetGlyphAtSize` 走 `FindGlyphNoFallback`。因此任何「运行时自建文本网格」的路线（`Font.GetCharacterInfo`、`TMPro.TextMeshPro`、`TextMesh`）在 1.7 都取不到汉字 —— 中文文本只能走**离线预渲染**或引擎自身的 **IMGUI** 文本路径（原版 `Verse.MoteText` 即 `DrawGUIOverlay` + `GenMapUI.DrawText`）。
  - **动态字体请求与查询必须同尺寸**：`Font.RequestCharactersInTexture(s, size, style)` 与 `Font.GetCharacterInfo(c, out ci, size, style)` 的 `size` 必须一致（`0` 表示字体默认尺寸），否则字形位置与前进量会错乱（见 B-04 BUG-030）。
  - **同帧批量创建/销毁临时对象须用 `DestroyImmediate`**：`Object.Destroy` 延迟到帧末，同帧内连续「建 → 渲染 → 销毁」会让上一批对象残留在相机视野里（见 B-04 BUG-029）。
  - **1.7 的死亡路径会立即销毁原 Pawn**：致死伤害在 `PostApplyDamage` 回调里到达时，受害者已 `Destroyed`。凡在该回调里做归因 / 统计，判敌对必须用 `Faction.HostileTo`，不能用 `Thing.HostileTo(Faction)`（后者对 `Destroyed` 直接返回 false，见 B-04 BUG-033）。1.6 的 `Pawn.Kill` 不销毁原 Pawn，两版行为不同。

## 命名与命名差异

- 框架类前缀约定：`Patch_*` `Spell_*` `Skill_*` `DevelopableAbility_*` `Mote_*` `UI_*` `StatPart_*` `QuestNode_*` `JobDriver_*` `GameComponent_*`。
- **Harmony 补丁命名与组织**：补丁类一律 `Patch_*` 前缀，且**以「相关功能/内容」命名**——
  - 技能/魔法/发展能力直接取其名：`Patch_TheWorld`、`Patch_Railgun`、`Patch_LuckOfTheSea`、`Patch_Ember_PreventDeath`、`Patch_Ember_Capacities`
  - 成长类用 `<能力值>Gain_<来源>`：`Patch_StrengthGain_Kill` / `_Down`、`Patch_EnduranceGain_Damage` / `_Heal` / `_Nutrition`、`Patch_DexterityGain_Craft`、`Patch_AgilityGain_Move` / `_Dodge`、`Patch_ManaGain_Entropy` / `_NeedsPsyfocus` / `_HasPsylink` / `_PsyfocusFall`、`Patch_SkillGrowth`、`Patch_WillGain_Meditate` / `_Inspiration` / `_Charity` / `_Interaction`
  - 系统类用系统名：`Patch_Virtue_Trigger`、`Patch_VirtueControllable_*`、`Patch_AbnormalResistance_*`、`Patch_GuildEnvoy_Talk`、`Patch_FamiliaTab_PreOpen` / `_Draw`
  - **不以被补丁的原版类型命名**（避免 `Patch_RecordsUtility_PawnKilled`、`Patch_Pawn_PathFollower` 这类与功能脱节的写法）
  - 单类文件的类名 = 文件名；一个文件可含多个补丁类（不强制一文件一类），此时统一用「文件名前缀 + 语义后缀」；命名空间统一 `FamiliaMyth.Patch`
  - 唯一例外：`HistoryTabHelper.cs` 内含 UI 工具类（属 `FamiliaMyth.UI`）与 2 个补丁类（写在同文件的 `FamiliaMyth.Patch` 块内），文件名取工具类名
- **Harmony 补丁目标写法**：优先 `[HarmonyPatch(typeof(X), nameof(X.Y))]`（编译期可校验）；**原版方法为 private/protected、或类型为 internal 时**只能用字符串形式（如 `Pawn_PathFollower.TryEnterNextPathCell` 为 private、`WorkGiver_FightFires` 类型为 internal），此时须格外注意拼写与原版版本变更。
- **补丁异常防护**：所有 `Prefix/Postfix` 方法体必须 `try-catch` + `Log.Error($"[FamiliaMyth] {nameof(补丁类)} error: {ex}")`；`Prefix` 的 catch 必须 `return true` 放行原版逻辑（返回 false 会静默屏蔽原版方法，是最危险的写法）；成对 `__state` 的 Prefix 出错时写入让 Postfix 短路的哨兵值（`IntVec3.Invalid` / `-1` / `float.MaxValue`），Postfix 首行校验并跳过。
- **本地化：四条文本路径（均有反编译 / 原版实证，勿混用）**：
  1. **Def 字段**（`label` / `description` / `letterText` 等）→ `DefInjected`，键名 `<DefName>.<字段路径>`；列表字段用索引（`roles.0.label`、`outcomeChances.1.label`、`stages.0.description`）
  2. **语法规则列表**（`questNameRules.rulesStrings` / `questDescriptionRules.rulesStrings`）→ `DefInjected` 整表替换：`<DefName>.questNameRules.rulesStrings` + `<li>`
  3. **任务脚本节点文本**（`SlateRef<string>` 字段，如 `QuestNode_Letter.label` / `QuestNode_SiteClearanceReward.letterLabel`）→ Def 元素加 `TKey="引用名"`，语言文件键 `<DefName>.<引用名>.slateRef`（反编译依据：`SlateRef<T>` 内 `[MustTranslate_SlateRef] private string slateRef;`）
  4. **代码内文本** → `Keyed` + `"Key".Translate()`，键名规范 `FamiliaMyth.<域>.<语义>`（域用 PascalCase 功能名，如 `FamiliaMyth.QuestLetter.Accept`）
- **Def 字段不会自动 Translate**（取证：`Verse/Def.cs` 的 `LabelCap => label.CapitalizeFirst()`、`TaggedString(string)` 仅赋值、`Verse.AI/MentalState.cs` 的 `GetBeginLetterText()` 均不 Translate；`LoadedLanguage` 的 `Keyed` 与 `DefInjected` 是两套独立加载）。因此**切勿把 Keyed 键填进 Def 字段**——它不会被翻译，只会把该键原样显示在游戏里；原版 `Data/` 中 0 处此写法（本项目历史遗留 58 处已于本地化迁移中修复）。
- **Def 内文本一律保留**（作为默认文本与兜底），由 `DefInjected` / `TKey` 覆盖；**不要清空 Def 内文本**——语言键缺失时会退化成 defName。原版模式即：`<label TKey="Xxx">Default text</label>`。
- 本地化完整性检查脚本：根目录 `12-本地化检查.ps1`，共 7 项 —— ①Def 文本覆盖 ②任务 TKey→slateRef ③rulesStrings 规则列表 ④错误 key 占位 ⑤Keyed 中英差集 ⑥代码内 Translate 键覆盖 ⑦**XML 类型引用 → 源码类型可解析性**（类名重命名/笔误导致 `Could not find a type named ...` 的加载期红字，靠此项自动兜住；方法引用 `Type.Method` 视为合法）。
- **`"Key".Translate(...)` 的参数语法不是 `string.Format`**：它走 `TranslatorFormattedStringExtensions` → `TaggedString.Formatted` → `Verse/GrammarResolverSimple.cs`，解析器 `TryResolveInner`（line 155-168）**一遇 `:` 即切「函数调用」模式**（`{func:args}`），因此 **`{0:F0}` / `{0:P0}` 这类格式说明符一律不可用**；`Verse/LanguageWorker.cs` 的 `ResolveFunction`（line 254-264）只认 `lookup` / `replace`，其余分支**静默 `return ""`**——不报错、不打日志、检查脚本也查不出，表现为该参数位置**显示为空**。需要格式化时先在参数侧 `value.ToString("F0")` / `value.ToStringPercent()`，再作为普通 `{0}` 传入。无参 `.Translate()` 直接查表返回原文（不做符号解析），所以文本里含 `{BASETEXT}` 等二次占位符是安全的，但**这类 key 今后不可带参数调用**（否则触发 `Could not resolve symbol` 的 Log.ErrorOnce）。见 B-04 BUG-024。
- **纯前缀/符号类文本（如倍数符号 `x`）拼在代码侧，不写进 Keyed 值**：写到键值里时，首字符大小写曾在游戏内与文件不符（键值为小写 `x`、显示为大写 `X`；`Translate` 链路逐行核对均不改大小写，机制未查明）。原版 101 处调用点一律自行拼接（`RimWorld/StatPart_Age.cs:39`、`RimWorld/StatPart_Quality.cs:57` 等），本模组照此写法即正常。见 B-04 BUG-032。
- **神名系统（三位一体的两个视角，勿合并）**：`FamiliaMythMod` 持有三样东西——玩家视角默认名 `DefaultGodName1`（Keyed `FamiliaMyth.DefaultGodName1`，中文"你"／英文"You"）、眷族视角默认名 `DefaultGodName2`（"神明"／"My god"）、敬称 `Honorific`（"大人"／英文留空）。`godName` 是**只读属性**，直接取**当前文化的主神名**（`Ideo.KeyDeityName`，即文化 `fixedDeityNameTypes` 中该神灵的 `name`），文化不存在或无神灵时为 null；`GodAddress = (godName ?? DefaultGodName2) + Honorific` 供**眷族口吻**文本使用，玩家视角文本则用 `godName ?? DefaultGodName1`。以 `{god}` 参数注入（仪式信件、美德祷告飘字）。
  - 英文侧句法约定：`DefaultGodName1` 落在主语位，动词一律用**一般过去式**（`{god} bestowed Pharna upon {pawn}`），规避 "You has / You have" 的人称变化；所有格位置**不用** `{god}'s`（默认值为 You 时会拼成 "You's"）。
- **模组设置数据走原版 `ModSettings`**：`FamiliaMythSettingsData : ModSettings`（字段 `public bool guildContent` + 六条 `SimpleCurve`，`ExposeData` 内 `Scribe_Values.Look(ref guildContent, "guildContent", false)` 与逐条 `Scribe_Deep.Look(ref curveXxx, "curveXxx")`）由 `FamiliaMythMod.SettingsData => GetSettings<FamiliaMythSettingsData>()` 取得。`Mod.GetSettings<T>()` 自动读写 `Config/Mod_<FolderName>_<模组类名>.xml`——`modHandleName` 取**模组类名**而非设置类名，本模组即 `Mod_Familia_Myth_FamiliaMythMod.xml`；文件不存在时静默按默认值处理（不报错）。曲线读档缺节点时以内置默认副本补位（`ScribeCurve` 读前读后各兜一次）。
  - `FamiliaMythSettings` 只做门面：静态 `GuildContentEnabled` 供 `GameComponent_FamiliaRankTracker` / `IncidentWorker_GuildEnvoy` 四处调用点读取；`Curve(statusType)` / `ResetCurve` / `ResetAllCurves` 供 `PharnaCurve` 与设置页读写；`Data` 在设置未就绪时为 null。`PharnaCurve.GetCurve` 取不到配置时回落内置默认。
  - 设置页已接入原版「选项 → 模组选项」：`FamiliaMythMod.SettingsCategory()` 返回 `FamiliaMyth.Settings.Category` 的翻译值（**非空即出现在列表**，同时作列表名与窗口标题），`DoSettingsWindowContents` 转 `UI.UI_SettingsPage.Draw`。页面结构为两级折叠：`实验性内容`（公会开关）与 `数值配置` → 子标签 `映射曲线` → 六条曲线行（手风琴，同时只展开一条）+ 行内 `UI_CurveEditor` 绘图区（拖点吸附 100 / 双击加点 / 右键删中间点 / 悬停指示；深底浅网格自绘、正方形 1:1）。
  - 设置页滚动：`UI_SettingsPage.Draw` 在 `DoSettingsWindowContents` 内**自开一层** `Widgets.BeginScrollView(inRect, ref scrollPosition, viewRect, true)`，`viewRect` 宽为 `inRect.width - 20`（让出滚动条）、高取上一帧实测的 `contentHeight`（首帧退化为 `inRect.height`）。可行原因：外层 `Dialog_Options` 的滚动高度取自 `listing.CurHeight`，而直接 `DoSettingsWindowContents` 不推进该游标 → 外层内容高为 0 不滚动，内层滚动条才是唯一生效的一层（同 RimTalk Memory Patch 3608181242 的做法）。曲线绘图区据此可为正方形（`PlotSide = 300`）而不被窗口下沿截断。`PreClose` 才调 `WriteSettings()` 落盘。
- **美德心声（触发飘字）**：`MentalState_Virtue.PostStart` 末尾用 `MoteMaker.ThrowText` 飘出眷族的一句话，`Rand.Bool` 在 `FamiliaMyth.Virtue.Whisper.*`（独白，不点破神存在）与 `FamiliaMyth.Virtue.Prayer.*`（祷告，含 `{god}`）之间随机择一，键后缀即 `VirtueType` 枚举名。**飘字必须放 `PostStart` 而非 `TryTriggerVirtue`**：后者是"先赋值 `currentVirtue` 再 `TryStartMentalState`"，启动失败时会飘出并不存在的美德；`PostStart` 由引擎在状态确实开始后回调，且与光环特效同拍，一次性语义也正确（读档不会重放）。
  - **成长双衰减**：`实际增量 = 基础增量 ÷ (1 + 单项超量/500) ÷ (1 + 总量超量/2500)`；单项超量 = `max(0, 该项当前值 − 400)`、总量超量 = `max(0, 六项当前值之和 − 2000)`；**未超阈值时保持正常线性增长**
  - `Hediff_Pharna.TotalStatus` = 六项 current 之和，即「本周期累积经验」——`Ascend()` 清零 current 时天然归零，**无需新增字段与 Scribe**
  - 参数集中在 `Hediff_Pharna.cs` 顶部 4 个 const：`StatDecayThreshold(400)` / `StatDecayScale(500)` / `TotalStatDecayThreshold(2000)` / `TotalStatDecayScale(2500)`
  - **设计意图**：该阈值组合使「专精 1~2 项」几乎不触发总量衰减（专精 1 项时 `TotalStatus` 最高仅 999 < 2000），而「平均 6 项」在每项 333 时就触发 → 数学上逼出「只养 2~3 项」的养成取向
  - **k 的构成与上限**：`k = current + potential`（实现锚点：`GetFinalStatus` 以 `GetFullStatus` 为基准，再叠加技能 / 发展能力 / hediff comp 的 `IStatusModifier` 修正）；current 每级上限 999（`maxStatus`）、等级上限 Lv10（`HediffDef.maxSeverity`——原版 `Hediff_Level.ChangeLevel` 即用 `def.maxSeverity` 夹取）→ **k 天然封顶 9990**
  - **效果系数锚点**：`k ≈ 4000`（Lv5 实际水平）≈ 原版精锐（动力甲 + 传奇武器 + 技能 20）的 1.2~1.5 倍；`k = 9990`（Lv10 理论满）不设强度上限，靠养成难度限制可达性
  - **伟业（Feat）只来自战斗事实**：任务侧只发评级升级点数，不发放伟业（旧的固定量 `DailyExploits = 500` / `RankUpExploits = 900` 已废弃）；`CalculateTaskParams` 的 `points`（原版点数 × `PharnaGrowthFactor`）**仅用于标定任务难度**，仍保留
  - **魔力系统（三层资源链）**：精神力（原版 psyfocus，0~1）→ **魔力**（`Hediff_Pharna.manaPool`）→ 魔法效果，两个过程都产**心灵熵**。常数集中在 `Hediff_Pharna.cs` 顶部：`PsyfocusPerSecond(0.0025)`（每秒投 0.25% psyfocus）、`ManaPerPsyfocus(1000)`（每 1% 精神力折算 1000 点魔力 → 基础每秒 2.5 点）、`EntropyPerPercent(1)`（每 1% 产 1 点熵）、`ConvertIntervalTicks(60)`（每秒结算一次）
  - **上限与效率**：`ManaMax`（基础 100，`val + k × 0.75`）与 `ManaConversion`（基础 1，`val + k × 0.001`）均由**魔力**经 `StatPart_Pharna` 注入；魔法强度由 `ManaControl` 家族（原 `SpellPower`）承载，**魔力不再直接加法强**
  - **字段命名勿混**：`Hediff_Pharna.mana` 是六维属性「魔力」，资源池是 **`manaPool`**（属性改名会破坏存档）
  - **消耗统一走 `SpendMana()`**：扣池的同时按「每点消耗的魔力（`ProfGainPerMana = 0.0005`）」喂魔导熟练度；`RefundMana()` 供按时长回滚（如 The World 提前结束）
  - **意识影响用原版 `capacityFactors`**：`<capacity>Consciousness</capacity><weight>1</weight>`，`StatWorker.cs` 以 `Lerp(val, val × 能力因子, weight)` 结算 → 零代码、受伤即生效、属性面板自动显示
- **批量修改 XML 数值的安全做法**：先备份目标文件 → 用「按块替换」（`[regex]::Replace` + MatchEvaluator，以 `Match.Index` 为基准）而非「绝对索引拼接」——后者会把数值插进标签中间、造成 XML 损坏 → 改完必须 `[xml]` 解析校验，失败立即从备份回滚。

- 新增窗口类继承 `Window_FamiliaBase`（内容区模板 + `FitInitialSize` 尺寸换算 + 文本状态保护）；不保留顶部标题带的窗口把 `HasHeaderArea` 置 false。
- 随机取样前必须校验候选集合非空，集合可能为空时提供兜底数据（空集合取随机索引会越界，见 B-04 BUG-026）。
- 需要跨存读档稳定的随机结果（如升华奖励）时，用 `Rand.PushState(种子)` / `finally Rand.PopState()` **只包住抽样步骤**：建池与实例化本身可能消耗 Rand（如魔法阵样式首次随机生成），一并包进去会破坏结果确定性。种子应由**已持久化**的数据组合而成（如 `pawn.thingIDNumber × 等级 × 本次会话的轮次`）。
- 强制窗口（`doCloseX = false` + `closeOnCancel = false`）内的任何刷新 / 重建逻辑都必须保证内容非空：内容为空则玩家无法关闭窗口而卡死；刷新失败应整体回滚、保留原有内容。
- IMGUI 同一帧内重叠的交互区存在点击争用：一张卡上的多个可点区域（如卡片选择区与锁定栏）必须用**互不重叠**的矩形，不要依赖绘制顺序或 `Event.Use()` 兜底。
- 需要跨多次触发累积的软保底（如连续未获罕见升华奖励的次数）必须随 `ExposeData` 持久化，否则读档即失效；结算点取「玩家到手的结果」，不取「抽取批次」，以免与刷新次数互相刷分。
- **恩惠丢失重建的快照只存内存、不落盘**（`GameComponent_FamiliaMyth` 的 `Dictionary<Pawn, PharnaRecord>`）：唯一写入点是 `Hediff_Pharna.PostRemoved`（移除当拍即最后状态），故无周期扫描；代价是丢失后存档再读档不可救。快照只存 `defName` + 数值（不存 live `Spell` / `Skill` 对象），重建走统一工厂 + `Apply`，运行时状态（active / 冷却 / 充能）不恢复。
- **`Pawn` 可作 `Dictionary` 键**：`Verse.Thing` 只提供 `public bool Equals(Thing other)`、未覆写 `object.Equals`，`GetHashCode()` 返回 `thingIDNumber`（为 -1 时回退引用哈希）→ 字典按引用相等；只要 Pawn 已分配 ID（给予恩惠时必然如此）就不会哈希漂移。项目先例：`GameComponent_TheWorld` 的 `Dictionary<Pawn, IntVec3> fields`。
- **`Pawn_HealthTracker.AddHediff(HediffDef, ...)` 恒返回 hediff，不代表添加成功**：`HediffSet.AddDirect` 在 def 为 null 或部位缺失时只 `Log.Error` + `return`（静默失败）→ 重建 / 自愈后必须用 `GetPharna()` / `hediffSet.hediffs.Contains` 复核。
- **读档期 hediff 被摘除不触发 `PostRemoved`**：`Hediff_Level.ExposeData` 的 `PostLoadInit` 在 `Part == null` 时直接 `pawn.health.hediffSet.hediffs.Remove(this)`，绕开 `RemoveHediff` → 靠 `PostRemoved` 捕获的机制在读档期收不到通知，须在自己 `ExposeData` 的 `PostLoadInit` 里自检。
- **死亡信追加文本的挂载点**：`HealthUtility.GetDiedLetterText` 的 Postfix 只能拿到「死因正文」，追加内容排在借用殖民者 / precept / 动物等后续段落**之前**；要永远位于最末须改挂 `LetterStack.ReceiveLetter(Letter let, ...)`。

## 伟业（Feat）体系的长期约定

- **四层职责**：检测（`GameComponent_FeatTracker` 扫描战斗与归属）→ 分析（`FeatContext` 把战斗事实压成数据包）→ 判定（`FeatTraitJudger` 子类逐条给 bool 与系数）→ 记录（`FeatRecord` 存进 `Hediff_Pharna.feats`）。**判定层不得反向依赖记录层**，新增性质只加一个判定器 + 一条 Def。
- **量度必须绝对**：单场战斗的基础量度是敌方 `PawnKindDef.combatPower` 之和（`threat`），**不除以我方实力**——相对成长由敌方点数携带的 `PharnaGrowthFactor` 承担。「人多不算伟业」「等级越高越难」由公式自然涌现，不另写规则。
- **得分两级拆分**：`battleMagnitude = threat × Π(各性质 multiplier)` → `personalScore = battleMagnitude × share` → 再按**个人**阈值表分档。同场战斗的每个参与者拿同一份 `battleMagnitude`，差别只在 share。
- **贡献三路径加权**：`dealt × DamageWeight(1.0) + taken × TakenWeight(0.5) + support × SupportWeight(1.0)`（权重是 `FeatTraitDef.cs` 顶部私有 const）。只统计**本阵营**成员、只统计**本阵营 ↔ 敌对**方向的伤害——敌方内讧、友军误伤与脚本伤害一律不得计入个人贡献。
- **分母跟随战果、不跟随我方**：`share = 个人贡献 ÷ 战斗贡献总额`，战斗贡献总额 = **敌方承受的全部伤害**（不分来源：我方 Pawn、炮塔、商队、陷阱、火灾与屋顶等环境伤害都算）+ 我方参战者 `taken × 0.5` + 我方参战者 `support × 1.0`。① 我方 Pawn 的 `dealt` 已包含在敌方受损里，**分母不得重复计入**；② 分母不再是我方内部之和，外部力量完成的战果会按比例吃掉所有人的份额——「靠阵地 / 炮塔 / 商队磨死敌人，再蹭一点伤害混高分」由此被堵住，这是该口径存在的唯一理由。
- **支援（support）只计作用于他人者**：立即型治疗在 `HealHelper` 三个工具方法内按真实量上报（治愈 1:1、包扎与恢复部位 ×0.3），归属靠末位 `Pawn healer` 参数；持续型效果（愈合光环、疼痛抑制、嘲讽）挂 `HediffComp_FeatSupport`，按**实际生效 tick** 累计、每 60 tick 上报一次，贡献度在 XML 配 `<supportPerSecond>`；无 Hediff 载体的控制（时停、光球眩晕）在施加点按 `ControlPerSecond` 折算。**自我治疗与自我增益一律不计**（`healer == target` 过滤）——其收益已体现在自身的 `dealt` / `taken` 中；唯一例外是「挂在自己身上却作用于敌人」的嘲讽，由 XML 的 `allowSelf` 显式声明，不写死在代码里。
- **不做 `Hediff_Injury.Heal` 补丁**：该方法同时承载**伤口自愈**（`Hediff_Injury.Tick` 驱动）与原版包扎加速，补丁拿不到施术者、会把玩家的自然愈合也计进去。因此治疗归因一律走本模组自己的入口，未经 `HealHelper` 的恢复（自愈、原版包扎、第三方 mod）**刻意不记**。
- **`HediffComp` 的持久化钩子是 `CompExposeData()`**（不是 `ExposeData()`），另有 `CompPostTick(ref float)` / `CompPostPostAdd(DamageInfo?)` / `CompPostPostRemoved()`；组件内的运行时状态（如支援组件的 `caster` / 未上报余量）必须写在 `CompExposeData` 里。
- **阈值表按「典型小队份额」标定**：`FeatUtility.TierThresholds` 9 档以 3~4 人小队（份额 25%~33%）为基准，单人打同样的仗自然拿到约 N 倍档位——这是**有意保留的额外奖励**，不是失衡。**分母纳入外部战果后实际份额整体下降，九档阈值需按实机重新标定**（现数值尚未按新口径校准）。
- **档位与升华 1:1**：9 档阈值 ↔ 9 次升华（Lv1→Lv10，`HediffDef.maxSeverity = 10`），`RequiredTier(level) = level`；`AvailableFeat()` 在「未使用（`usedForLevel < 0`）且档位 ≥ 当前等级」中取**档位最低**者（刻意如此，保证升级消耗的是最不浪费的一笔）。
- **判定与数据解耦**：性质由 `FeatTraitDef.judgerClass` 指向 `FeatTraitJudger` 子类，统一经 `FeatTraitJudger.Create(def)` 构造（与 `GuildQuestGenerator.Create(def)` 同构，禁止绕过统一工厂）；判定只看战斗事实包，不看来源、派系与叙事。目前**没有任何判定器覆写 `Multiplier(ctx)`**，故 UI 展示性质系数时直接取 `def.multiplier` 即为结算值；若将来有判定器改为按战斗事实动态给倍率，必须把**实际倍率**一并存进 `FeatRecord`，否则卡片展示与结算不符。
- **复用原版 Battle 日志的硬约定**：① `Battle` 的「结束」只是**入口关闭**，成员在 `Battle.TicksForBattleExit`（5000 tick）内仍算在册，故归属修正必须在结算前跑——`RenormalizeContributions` 按 `pawn.records.BattleActive`（其内部已沿 `AbsorbedBy` 取末端）重挂条目，`BattleActive == null`（结算当拍恰好过期）时**保留原 battleId** 而非丢弃；② 同一 `(battleId, pawn)` 键可能被重挂多次，**必须按字段求和合并**，不可覆盖；③ 去重集合用 `pawn.GetUniqueLoadID()` 字符串并写入 `ExposeData`，跨存档仍有效；④ 战斗日志**不记录伤害数值**、也不区分攻守，所以伤害必须靠 `Patch_FeatContribution`（`Pawn.PostApplyDamage`）自行归因，日志只用来取「谁与谁交过手」。
- **战斗名在结算时快照**：原版 `Battle.GetName()` 是**按需生成且会被清空的缓存**——每次 `Add(entry)` 与 `Absorb` 都把 `battleName` 置空，名称按当时的参与者与派系现算（Solo / Duel / Internal / War / Brawl），而 `Battle` 在 `BattleLog` 中只保留 20 场，**事后无法反查**；因此必须在 `Resolve` 时取一次并存进 `FeatRecord.battleName`，UI 只读该字段。取名依赖参与者与派系的 Grammar 解析，**必须包 try-catch**；失败或旧存档无此字段时统一显示占位词。
- **术语固定**：伟业 = **Feat**（不再用 Exploits）；发展能力 = **Developable Ability**（不是 Developmental）；武器同调 = **Weapon Attunement**，其内部的武器熟练度 = **Weapon Proficiency**。改名后须同步 `docs/C/C-06-本地化术语表.md` 与 `Languages/` 全部文案。
