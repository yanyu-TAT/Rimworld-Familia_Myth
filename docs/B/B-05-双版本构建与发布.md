# B-05 双版本构建与发布

> RimWorld 1.7 起游戏运行时由 Mono 换成 CoreCLR（.NET 10，Unity 引用面被 `UnityStubs` 取代），1.6 与 1.7 的编译引用面完全不同。本模组同时支持两个版本：**一份源码、一个 csproj、双目标框架**，产物由 `LoadFolders.xml` 按游戏版本装载。
> 结构改动与构建命令以本文件为准，AGENTS.md「常用命令」只列入口。

## 一、目录与装载

```
Familia_Myth/
├── About/About.xml          # supportedVersions: 1.6 + 1.7
├── LoadFolders.xml          # 按游戏版本选择版本目录
├── Source/  Defs/  Patches/  Languages/  Textures/  Materials/  AssetBundles/   # 两版共享
├── Familia_Myth.csproj      # 双目标：net472（1.6）/ net10.0（1.7）
├── 1.6/Assemblies/Familia_Myth.dll
└── 1.7/Assemblies/Familia_Myth.dll
```

```xml
<loadFolders>
	<v1.6><li>/</li><li>1.6</li></v1.6>
	<v1.7><li>/</li><li>1.7</li></v1.7>
</loadFolders>
```

- `<li>/</li>` 装载共享内容；版本目录提供该版本专属的 `Assemblies/`。
- ❌ **mod 根目录不得保留 `Assemblies/`**：`<li>/</li>` 会把它一并装载，导致两个版本的 DLL 同时进入游戏并冲突。
- 版本目录命名与 `LoadFolders.xml` 的 `<vX.Y>` 对应（参照 Harmony 的社区惯例）。

## 二、引用副本 lib\<版本>

`lib/` 存放从游戏与创意工坊取回的程序集副本，`csproj` 的 `HintPath` **只指向它**，不指向 Steam 目录：

- 好处一：编译期不依赖 Steam 安装状态，两台机器/两版游戏可同时编译；
- 好处二：Steam 只能装一份游戏，切版本会删除另一版的文件，指向 Steam 必然踩空。

`lib/` 在 `.gitignore` 中，**不入库**（Ludeon 与第三方程序集不随本仓库分发）。

刷新方式（需先把 Steam 切到目标版本，脚本会校验游戏 `Version.txt`）：

```powershell
pwsh -File .\13-同步引用库.ps1 -Version 1.6
pwsh -File .\13-同步引用库.ps1 -Version 1.7
```

脚本会把游戏版本、文件大小与 SHA256 前 16 位写入 `lib\<版本>\_refs.txt`，便于核对编译产物对应的游戏版本。

| 版本 | 来源 | 关键文件 |
| --- | --- | --- |
| 1.6 | `RimWorldWin64_Data\Managed\` | `Assembly-CSharp`、**`mscorlib`**、`netstandard`、`UnityEngine` + `CoreModule` / `IMGUIModule` / `InputLegacyModule` / `TextRenderingModule` / `UIElementsModule` / `ImageConversionModule` |
| 1.7 | 游戏根目录 | `Assembly-CSharp`、`UnityStubs`、**`Waylith`**（`Waylith.UnityCompat` 备用） |
| 两版 | 创意工坊 | `0Harmony`（Harmony `294100\2009463077\<版本>\Assemblies\`） |

## 三、构建

```powershell
dotnet build Familia_Myth\Familia_Myth.csproj              # 两个版本一起编译
dotnet build Familia_Myth\Familia_Myth.csproj -f net472   # 只编 1.6
dotnet build Familia_Myth\Familia_Myth.csproj -f net10.0  # 只编 1.7
```

csproj 关键设定：

- `TargetFrameworks` = `net472;net10.0`，按 `$(TargetFramework)` 条件切换引用与输出目录；
- `AppendTargetFrameworkToOutputPath=false` + 每个目标的 `OutputPath` 指向 `<版本>\Assemblies`；
- `IntermediateOutputPath` = `obj\$(Configuration)\$(TargetFramework)\`——**必须显式隔离**，否则两个目标的中间文件互相覆盖，并行构建时随机失败；
- 所有 `<Reference>` 写 `<Private>false</Private>`，否则程序集会被复制进输出目录，既污染 mod 又随游戏加载；
- 版本分叉代码用 `RW16` / `RW17` 预定义符号。

## 四、已踩的坑

| 现象 | 根因 | 处理 |
| --- | --- | --- |
| 1.6 报 `CS8701 目标运行时不支持默认接口实现` | 项目用 C# 8 默认接口实现（`IAscendReward`、`Spell` 等），而 .NET Framework targeting pack 的 `mscorlib` 不支持；原 csproj 用的是 **Mono 的 mscorlib** | 引用 `lib\1.6\mscorlib.dll`（取自游戏 `Managed\`）覆盖默认程序集 |
| 1.7 报 `CS0012 类型 DrawPropertyBlock/Material/TextMesh 在未引用的程序集中定义` | 1.7 的 `UnityStubs.dll` 只提供 Unity 类型存根，实际定义转发到运行时程序集 `Waylith.dll` | 引用 `lib\1.7\Waylith.dll` |
| 输出目录被几十个第三方 DLL 填满 | 引用未标 `<Private>false</Private>`，默认 `true` 会 CopyLocal | 所有引用统一标注 |
| `obj\Release` 下无 TFM 子目录 | 设了 `AppendTargetFrameworkToOutputPath=false` 后中间路径也失去 TFM 区分 | 显式设置 `IntermediateOutputPath` |
| 1.7 报 `CS1061 TextMesh 未包含 font / characterSize / fontStyle` | 1.7 的 `UnityEngine.TextMesh` 只剩 `color` / `text` / `fontSize` / `anchor` / `alignment` 五个成员 | 弃用 TextMesh，改 `Font.GetCharacterInfo` 逐字排版并自建 Mesh（`CharacterInfo` 两版字段一致，零额外依赖） |
| 1.7 报 `CS1503 DrawMesh 的参数 2..11 无法转换` | 1.7 没有 `DrawMesh(Mesh, Vector3, Quaternion, Material, …)` + 三个 bool 的重载，只剩 `Matrix4x4` 形式 | 统一改用 `Matrix4x4.TRS(...)` 形式——该重载 1.6 / 1.7 都有，无需 `#if` |
| 1.7 输出目录出现 `Familia_Myth.deps.json` | .NET 10 默认生成宿主依赖清单 | `GenerateDependencyFile=false` |
| 1.7 下咏唱词完全不可见（或只报「字体未提供任何字形」） | 1.7 的文本后端 `ImGuiTextMeshProBackend` 只烘焙 ASCII / Latin-1 字形（`FindGlyphNoFallback`），不提供任何中文字形；`Font.CreateDynamicFontFromOSFont` 是空实现，`TMPro.TextMeshPro` 也走同一个后端 | 改为离线预渲染：1.6 下用现成烘焙管线导出 PNG 到 `Textures/Incantation/`（Debug 指令「导出咏唱词纹理」），运行时 `ContentFinder` 优先加载；自定义 shader 与粒子动画不用动 |
| 不带 `-f` 的整项目构建报「生成失败」却 `0 个错误`（单个目标构建均正常） | cross-targeting 的两个目标被并行调度，中间文件与输出互相干扰 | csproj 设 `<BuildInParallel>false</BuildInParallel>` |
| 1.7 下自定义 shader 效果整体丢失，日志报 `no Vulkan variant in this bundle ... it draws with the engine default` | 导出的 AssetBundle 不含 Vulkan 变体（1.7 引擎跑在 Vulkan 上） | 用 Unity 重新导出并确保目标平台 Graphics APIs 含 Vulkan；打包脚本见 C-03「`.shader` 打包」 |

## 五、发布前检查清单

- [ ] 两个目标框架均编译通过且无新增警告
- [ ] `1.6/Assemblies`、`1.7/Assemblies` 只有 `Familia_Myth.dll`（跑 `11.bat` 清理）
- [ ] mod 根目录不存在 `Assemblies/`
- [ ] `About.xml` 的 `supportedVersions` 含 1.6 与 1.7
- [ ] `Textures/Familia_Myth/Incantation/` 下的咏唱词 PNG 已随 mod 提交（缺失会导致两版都无咏唱词）
- [ ] 目标游戏版本内启动无红字（查 `Player.log`）
- [ ] 提交后打 tag（如 `v0.0.6`），`About.xml` 的 `modVersion` 与之一致

## 六、待办与已知风险

- 1.7 下 `Command_Spell.ProxyFor` 仍用 `FormatterServices.GetUninitializedObject`，编译产生 `SYSLIB0050` 过时警告（运行由 runtimeconfig 的 `EnableUnsafeBinaryFormatterSerialization` 放行）；若要消除，可 `#if RW17` 改用 `RuntimeHelpers.GetUninitializedObject`。
- 咏唱词纹理是**离线资源、运行时不再烘焙**：新增或修改咏唱词后，必须在 1.6 下用调试指令「导出咏唱词纹理」重新生成 PNG 到 `Textures/Familia_Myth/Incantation/`，否则该句在两版都不显示（`Player.log` 会报「缺少咏唱词纹理」并给出键名）。
- 1.7 处于公开测试期，游戏程序集会随更新变化：每次游戏更新后用 `13-同步引用库.ps1` 刷新对应版本，并核对 `_refs.txt` 哈希。
- 官方 `ModUpdating.txt` 尚未提供 1.6→1.7 变更清单，API 变更需自行反编译比对。
